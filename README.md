# Strange Room

**让物理上同处一室的人，像把设备摊在同一张桌子上一样共享文件。**

局域网直连，扫码即连，传完不留痕。没有账号，没有云端，不是网盘。

> **项目状态**：内部开发阶段。内核与命令行客户端有自动化测试覆盖（84 个用例，
> 含真实的端到端传输与断点续传），桌面端可以构建运行，但**界面尚未经过真机验收**。
> 详见文末「项目状态」。

---

## 它解决什么

会议室里，你想把 2GB 的素材给旁边的同事。现有做法都不顺：

| 做法 | 问题 |
|---|---|
| 微信 / QQ | 压缩画质、限制大小，还得先加好友 |
| 网盘 | 先上传再下载——同一间屋子里绕了一圈公网，数据还留在了云上 |
| U 盘 | 要拔插，还要找到那个 U 盘 |
| AirDrop | 只认苹果设备 |

Strange Room 的做法：你在自己电脑上开一个房间，屏幕上出现二维码；
对方扫一下就连上，文件走局域网直传。1GB 是几秒钟的事，不是"等着上传"。

## 现在能做什么

### 桌面端

分享者：打开应用 → 把文件或文件夹拖进窗口（或用「选择文件…」）→ 点「开始分享」→
屏幕出现二维码。

接收者：扫二维码拿到连接串（或直接粘贴）→ 选保存目录 → 点「接收文件」。

界面只有四个状态：**首页 → 等待接收（二维码）→ 传输中（进度）→ 结果**。
另有「诊断网络」按钮：连不上时先跑它，而不是自己猜。

### 命令行

```bash
cargo build --release

# 分享（会打印二维码，等待对方接收）
./target/release/sr send ./photos

# 接收
./target/release/sr receive "srx1:..." --to ./downloads

# 网络自检：连不上时用它判断问题出在哪
./target/release/sr diagnose "srx1:..."
```

`sr send` 支持 `--port`、`--name`、`--no-qr`（只打印连接串，适合远程终端）。

### 桌面端怎么跑

```bash
cargo run -p sr-desktop
```

> 注意：仓库的 workspace 配置了 `default-members = ["crates/core", "crates/cli"]`，
> 所以日常的 `cargo build` / `cargo test` **不会**构建 Tauri（它的编译产物有 1–3 GB）。
> 只有显式 `-p sr-desktop` 时才会。

## 已经验证的能力

| 能力 | 实现方式 |
|---|---|
| 文件与文件夹传输 | 保留目录结构；相对路径经安全校验，绝对路径、`..`、Windows 保留名一律拒绝 |
| 完整性校验 | 每个文件传完用 BLAKE3 校验，不匹配就不改名为正式文件 |
| 断点续传 | 中断后只补缺少的部分，**而且会自动重连**（1s/2s/4s 退避，最多 4 次），不需要用户手动重跑。本地进度带**前缀内容哈希**——长度够不代表内容是我们要的，所以每次续传都真的核对前缀 |
| 指纹校验 | 只接受证书指纹与二维码一致的主机，不一致**秒级失败**并明确提示 |
| 大文件 | 流式读写，不把文件读进内存；接收前**真正预分配**空间，磁盘不足在传输开始前就报错 |
| 主动停止 | 协作式取消（不是杀进程）：已收部分保留，下次能接着传 |
| 网络自检 | 逐个候选地址真发握手探测，给出结论与可操作的排查建议 |
| 不留痕 | 全部成功后会清掉本地临时状态文件；不联网、不上传任何数据 |

实测：600 MB 文件在传输中被强杀后重连，只补传了缺的 452 MB，最终字节一致。

### 速度，以及为什么曾经慢

先给数字。回环基准（`cargo run --release --example bench -p strange-room-core -- 512`，
在一台 2 核 / 2.6 GHz 的虚拟机上）：

| 项目 | 速度 |
|---|---|
| 端到端传输（含加密、分帧、落盘、校验） | **185–205 MiB/s** |
| 磁盘裸拷贝（对照组） | 1113 MiB/s |
| BLAKE3 单线程（对照组） | ~1400 MiB/s |

修复前的局域网实测只有 **30–55 MB/s**，而其中大部分是白烧的。两个真实瓶颈：

1. **检查点把整个前缀重算一遍。** 续传检查点每 8 MB 写一次，每次都要重算"已收到的全部
   数据"的 BLAKE3，总开销就是 8+16+…+总大小，也就是 **O(n²)**——512 MB 的文件要哈希
   约 16 GB 数据，600 MB 的文件光这一项就是十几秒。它把吞吐按在 50 MB/s 上，而且在耗时
   归因里完全看不出来（看代码只会觉得"顺手算个哈希"）。现在改成边收边算、检查点只对
   哈希器取快照。
2. **UDP 套接字用的是系统默认缓冲区。** Windows 上只有 64 KB，而 QUIC 默认就允许
   1.25 MB 在途数据。内核缓冲区一满**直接丢包**：即使是在毫无真实损耗的回环上，丢包率
   都有 1.8%、17 次拥塞事件。现在收发缓冲都设成 4 MB，回环丢包归零。

修完之后，剩下的天花板是 **CPU**——传输期间约 1.5 个核跑满（Windows 上用户态 QUIC 每
字节的加解密与拷贝开销约 6–7 ns）。也就是说：在同一条 1 GbE 链路（上限 112 MB/s）或普通
WiFi（30–80 MB/s）上，**瓶颈已经回到链路本身**，不再是这个实现。

> ⚠️ **不要靠调大单流窗口来提速。** quinn 0.11 的接收缓冲最多容纳 1024 个不连续分片，
> 超过就以 `INTERNAL_ERROR("too many gaps in stream buffer")` 直接掐断连接（实测触发点
> 约 2.9 MB 未读数据）。默认的 1.25 MB 流窗口刚好在安全区内；要喂饱万兆链路得靠并行
> 多流，而不是加大单流窗口。回环上这曾让一次 512 MB 的传输在 4 MB 处就断掉。

## 工作原理

### 一次扫码，同时传递三件事

二维码里不只是地址，还有**会话 ID** 与**主机证书指纹**：

```
srx1:eyJ2IjoxLCJzaWQiOiI4ZjNj…   （base64url 编码的 JSON）
```

这让"怎么找到对方"和"怎么信任对方"用同一个动作解决——不需要 CA，不需要账号，
也不需要云端参与。信任锚点通过屏幕这个带外信道传递，**安全性等价于 Signal 的安全码比对**。

### 传输

QUIC（`quinn`）自带加密与多路复用；v1 用单条双向流跑完整会话。
协议层与传输解耦，将来换传输不影响上层。

### 分层

```
crates/core     内核：传输、协议、加密、续传、自检。不依赖任何 UI
crates/cli      sr send / receive / diagnose —— 也是长期的测试资产
crates/desktop  Tauri v2 桌面端：薄桥接层 + 原生 HTML/CSS/JS，不引前端框架
```

**内核与 UI 完全解耦**：内核只发出与界面无关的 `ProgressEvent`，
命令行用它画进度条，桌面端用它画进度条——桌面端**没有复制任何传输逻辑**。

## 运行平台

| 组件 | Windows | Linux | macOS |
|---|---|---|---|
| 内核 + CLI | ✅ | ✅ | ✅ |
| 桌面端 | ✅ WebView2（Win10+ 自带） | ⚠️ 需先装 WebKitGTK | ✅ 系统自带 WebKit |

**Linux 上跑桌面端**需要先装 WebKitGTK（Tauri 在 Linux 上用它，不是 Windows 那套 WebView2）：

```bash
sudo apt install libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev libayatana-appindicator3-dev
```

### 一处真实的平台差异：磁盘空间预留

- **Windows**：把文件长度改大（`SetEndOfFile`）会让 NTFS **真的分配簇**，等于预分配。
- **Linux**：同样的做法只产生**空洞**（稀疏文件）——`ls -l` 看着有 2 GB，实际一个盘块都没占。
  于是"磁盘满"会拖到传到 90% 才爆出来，正好是这一层要防的那种失败。

所以 Unix 上改用 `posix_fallocate` 真正预留空间。这是整个内核里唯一的平台差异，
代码在 `crates/core/src/fs_util.rs::preallocate`。

### CI 保证，而不是靠这句话保证

`.github/workflows/ci.yml` 在 Linux / Windows / macOS 三平台都跑测试与构建。
端到端用例是真的起 QUIC 端点互传文件、真的做断点续传，所以 CI 通过意味着
"能编译"并且"能传"。

## 开发

```bash
cargo test              # 内核 + CLI（默认成员），88 个用例
cargo test --workspace  # 连桌面端一起构建
cargo run -p sr-desktop # 跑桌面端

# 吞吐基准（回环，去掉网络变量）。这是长期的性能护栏：
# 任何改动让吞吐掉了，这里立刻能看出来。
cargo run --release --example bench -p strange-room-core -- 512
```

测试里包含真实起两个 QUIC 端点互传文件的端到端用例，以及「中断后重连只补差额」、
「**真的把连接掐掉之后自动重连带续传**」、「不可信检查点必须整文件重传」、
「指纹不符必须秒级失败」、「取消后必须还能续传」、「一个文件写不进去不能连累其他文件」
这类回归测试。

写测试时的一个规矩：修 bug 之前先把"能复现它"的用例写出来，并且**确认它在修复前真的
会失败**——否则那条测试只是个摆设。

## 项目状态

**已完成**：内核、命令行、桌面端界面、主动停止、网络自检、文件选择器、视觉系统。

**尚未验证**：桌面端的界面**没有任何人真正点过**。所有界面工作只验证到
「能编译、资源已嵌入二进制、逻辑有测试」。具体未验证的接线有三处：
拖拽、系统文件对话框、终端的 Ctrl+C。这三者的共同点是只有真实交互才能触发。

**已知限制**（现在还没有的，不要期待）：

- **没有自动发现设备**。必须扫码或粘贴连接串，不会自动列出同一 WiFi 下的设备。
- **没有公网能力**。仅限同一局域网；跨网段、AP 隔离、企业防火墙会连不上——
  这种情况下用 `sr diagnose` 或界面上的「诊断网络」定位。
- **没有移动端**。
- **没有安装包**。目前需要自己 `cargo build`，还没有做签名与分发。
- **主机停止分享后无法自己恢复**。接收端会自动重连（最多 4 次），但如果主机那边
  已经关掉分享或换了会话，二维码就作废了——这种情况必须重新扫码，任何自动重试都
  救不回来（会话 ID 与证书指纹都对不上了）。
- 仅支持同版本客户端互连（协议版本不匹配会明确报错）。
